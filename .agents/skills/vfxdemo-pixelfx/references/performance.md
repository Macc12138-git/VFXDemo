# 导入后的批次、合批与性能验证

目的：证明效果在给定并发、屏幕覆盖和目标环境下的成本，并在保留表现的前提下优化。
这一步属于后续 Unity 导入交付流程，不会由“更新 skill”自动触发。
当前 Brazier 的结构和真实播放已经验证，尚无本参考要求的批次/合批或目标设备测量。

## 1. 固定环境与基线

沿用 Unity 目标身份校验。记录效果/source/prefab/material/Shader 的版本或 hash、Unity/管线版本、
颜色空间、图形 API、设备/硬件、Editor 或 Player、构建模式、分辨率、Render Scale、相机、
HDR/MSAA/后处理、阴影、批处理配置及采样工具。诊断期间不随意修改项目全局设置。

记录目标设备、FPS/帧预算、正常和最坏并发、可接受的画质降级。缺少预算时先给本机实测，
将目标验收记为待定，不凭经验硬定“最多几次 Draw”。模拟器/Editor 不能代替真机结果。
捕获截图/GIF、Frame Debugger 和 Profiler 的开销互不混用；计时采样时关闭这些重型录制操作。

复用既有展示/测试场景隔离采样，不逐特效新建或复制场景。保护作者脏场景与既有布置，
临时测试实例或启停调整用后恢复，不保存测试用改动，也不往业务场景批量堆对象。
确需新专用场景时先取得明确指令，不能以性能测试为由默认创建。测试至少覆盖：

- 相同相机/背景的无特效基线；单实例；设计正常并发和压力并发。
  未知并发可先用 1/8/32 探查趋势，但必须写明这是探查，不是业务需求或通用标准。
- 循环效果暖机后稳定期；一次性效果的爆发峰值和尾声。同时触发与错峰触发按实际用途测试。
- 屏幕大面积重叠/近景，及典型游戏视距；相同数量不同覆盖可用于定位填充率问题。
- 反复 Play/Stop/Restart、启停重用、镜头外再返回；检查残留粒子、尾迹、Bounds 和内存趋势。
  在已有池化系统中集成需授权，测试工具不能成为特效运行控制依赖。

记录暖机/采样时长、帧数、重复次数和时序/seed。不要给一个截图的瞬时 FPS 盖章。

## 2. 先分清这些数字

| 项目 | 含义 / 不能替代什么 |
| --- | --- |
| ParticleSystem / Renderer 数量 | 结构规模，既不等于存活粒子数，也不等于 Draw Calls |
| 粒子数、顶点/三角形数 | 模拟与几何负载线索，不说明透明覆盖面积 |
| Batches / Draw Calls | 指定工具与相机/Pass 范围的实际绘制提交；注明统计口径 |
| SetPass Calls | 渲染状态/Pass 切换，不等于所有 Draw，也不是 GPU 时间 |
| SRP Batcher | 优化兼容绘制的 CPU 状态准备，不承诺把多个 Draw 变成一个 |
| GPU Instancing / Dynamic Batching | 依管线、Shader、Renderer 模式、平台及顶点流等条件才可能适用 |
| Overdraw / GPU ms | 透明多层、大 Quad 和复杂采样即使少 Draw 也可能很贵 |

“53 → 18 → 8 个系统”和“19 → 6 张图”只描述 Brazier 不同表达的规模变化，
而且画面/算法不同，不能冒充同条件优化收益或证实合批。

## 3. 真实定位批次和合批

在真实 Play Mode 的代表时相打开 Frame Debugger，定位该效果的渲染事件，记录相机/Pass、
Renderer、Shader/变体、材质、纹理、Blend、队列/排序和顶点流。对单实例与多实例分别检查，
注明哪些 draw 合并/未合并及工具显示的 break reason；工具未给原因时只能记录证据后的假设。
保存事件截图/可复查记录。Frame Debugger 用于结构诊断，不拿启用时的 FPS 作性能结论。

排查次序：

1. 意外的材质实例、不同贴图/关键字/Pass 或可避免的额外 Pass。
2. 不必要的逐 Renderer Sorting Order/Queue，导致透明物穿插打断原可复用的提交；
   排序是视觉约束，不能单为合批删除正确的前后关系。
3. 不同 Renderer 模式、顶点流/Custom Data 布局、网格及管线能力约束。
4. Instancing 是否真的适用于当前模式；粒子 Mesh 的 GPU Instancing 经验不可套到 Billboard。
   MaterialPropertyBlock 不保证合批，且可能改变 SRP Batcher 适用性，必须在实际配置检查。

优先复用兼容 sharedMaterial，把颜色、尺寸、相位等放原生数据；再评估静态素材合图/通道打包、
合并兼容系统或减少重复 Pass。静态 atlas 不是帧动画，但要测 UV、边缘串色和透明排序。
若本就由不同 Blend/排序/几何需求合理拆分，写明“保留拆分及成本”，不要承诺强行合成一批。

可用 Unity Stats 或已验证的计数器做快速读数，但必须给统计范围/空场景基线；
仅 Stats 数字不充分证明哪两个 Renderer 合批。没有 Frame Debugger/同等事件证据时，
明确“批次数已采样，合批机制未确认”，不要用同材质静态扫描替代实际证明。

## 4. CPU/GPU/内存与优化闭环

用 Profiler/ProfilerRecorder 或目标平台工具测量：

- CPU 主线程/渲染线程、粒子更新及提交成本、GC Alloc；注明各项是全帧还是效果相关 marker。
- GPU 帧时间及可获取的透明/粒子 Pass 成本，必要时看 overdraw、带宽和片元 Shader。
  无 GPU 数据或 marker 不支持时写“不可获取”，不当成 0 或用 CPU 时间代替。
- 稳态与峰值粒子数/几何量，纹理/材质/网格内存；重复启停后的增长和回收。
  PNG 磁盘大小不是 GPU 内存，资源计数也不是内存测量。

在固定条件下多次采样，记录 median、P95 和爆发峰值，保留原始 capture/采样表。
空场景差值只能作估算，CPU/GPU 并行与噪声会影响差分，不能保证线性按实例增长。

根据实测瓶颈选择最小变更：

- CPU/提交瓶颈：减少不必要系统/材质切换，简化高成本 Noise/碰撞/子发射；不要只看平均粒子数。
- GPU/填充瓶颈：裁透明空白、收光晕覆盖、减少烟层/采样/Pass；必要时提供经过验收的低档版本。
- 资源瓶颈：复用贴图、恰当分辨率/压缩/mip 与通道打包；无压缩只是本次美术基线，不是永久性能规范。
  平台压缩与噪声精度、细小笔触的画质变化要一并验证。

每次变更用相同场景、相机、并发与采样配置 A/B，记录前后指标、画面变化和副作用。
优化版用新版本/Variant，不能覆盖作者手调；若破坏已验收表现，保留原版并说明取舍，待确认。

## 5. 交付状态与证据

使用 [效果记录模板](../assets/effect-record.template.md)的性能表。至少给出：
空场景/单体/正常/压力的 Batches、SetPass、合批观察、CPU/GPU ms、粒子峰值、GC 和内存，
每项允许“未测/不支持”，但必须附原因、环境和后续条件，不能用默认零填充。

性能结论分层：`未测` → `本地基线已测` → `优化已同条件复测` → `目标设备预算通过`；
不适用项写明原因，不把这些层级与视觉验收合并成一个 passed。
预算或设备未给定时交付可播放版本、证据和缺口，不宣称“已适配低端机/生产优化完成”。
首次优化没有可测收益也可如实记录；停止无证据的反复重构，优先保证可读性与稳定性。
