# 案例驱动的技能迭代

本技能是持续扩展的制作工作流，不是由一个成功样例推导出的通用转换器。
入口保留 `vfxdemo-pixelfx`，新经验优先进入具体参考，不为每个效果再建一个重复主 skill。
作者已明确要求随本项目后续特效模板持续迭代此 skill：模板完成后回顾新增证据，必要时更新
对应案例与参考，不必为每次同范围复盘重复请求维护许可。普通试做的未验证尝试先留在作品记录，
没有新知识时不为凑更新改规则；不把临时尝试静默改成通用约束。
更新技能不等于更新个人记忆或重新获得资产重建权限；改变制作约束或扩大工作范围仍需说明。

## 每加入一个新模板，增加什么

在作品输出目录创建独立版本记录，例如 `Tools/PixelFX/output/hd/效果名/版本/effect-record.md`，
依据 [记录模板](../assets/effect-record.template.md)填写；记录留在 Assets 外，
特效 Docs 仅保留 Prefab 用法和 Inspector 参数位置，不附开发过程或测试报告：

1. 模板的用途/风格/来源许可、平台和镜头约束；把“应该如此”和“已经测得”分开。
2. 分层与实现决策：哪些静态素材、Shader、材质、原生模块/几何表达，以及备选被放弃的原因。
3. 视觉三轮改进、作者反馈、锁定来源 hash/options/seed 和导入指令；新版本不覆盖旧证据。
4. Shader/材质、结构/依赖、真实播放及性能测试的环境、证据路径、结果和未测项。
5. 真实遇到的问题 → 定位证据 → 最小修正 → 复测 → 哪类效果适用/不适用。

无证据的候选方法写“待试验”。工具脚本只有被实际调用验证后才写成可复用命令；
新源码不适配旧 exporter 时编写效果专用适配，不把菜单 Build 当通用转换入口。

## 什么应该更新到 skill

- **单案例经验**：加入案例参考并在本表标出覆盖范围，不扩大成硬约束。
- **多种独立效果反复验证的分工/检查方式**：提炼到 creation / shader-material / unity-native /
  performance 中；注明约束和反例。授权、保护手调和证据诚实属于共同约束，不靠样例数量决定。
- **具体错误/回归**：添加最小可复查检查或窄范围注意事项，不不断累加“所有效果一律”的补丁。
- **稳定可重复的人工操作**：先证明复用价值再抽成工具；效果参数留配置/案例，勿写死到主入口。

每次更新保持路径/命令可用，入口只补必要路由；UI 描述、AGENTS 和工作台同步，
不改上游 pixelfx 许可或把项目约定写回另一份 checkout。技能变更与作品版本记录分开。

## 接下来的覆盖方向（计划，不是已实现）

按作者后续提供的模板逐个验证；不主动扩大本次工作创建这些效果：

- 爆发/命中：短生命周期、峰值粒子、同步并发和末端收尾。
- 地面环/法阵：世界朝向、透视、深度遮挡和透明层排序。
- 斩击/光束/拖尾：Mesh/Trail、方向变化、UV 连续性和变换缩放。
- 投射物/附着：宿主移动与局部/世界模拟、重用后残留、与游戏逻辑的边界。
- 水/烟/大体积透明：透明覆盖、多层混合、移动 GPU 的采样/带宽。

这些方向用来发现技能不足，不是固定任务列表，也不要求所有效果套用相同层数或 Shader。

## 更新后的回归检查

先做 skill frontmatter/UI 元数据与所有引用路径校验，再用真实请求做只读流程走查：

- “先给高清预览”不会进入 Assets；“满意”不会触发导入。
- “导入，不要帧动画”选择静态素材/Shader/原生模块，不套旧图集。
- “检查合批”会找实际渲染事件，不把 SRP Batcher 或系统数当结论。
- “未给手机型号”能给本地结果与缺口，不宣称真机达标。
- “新模板与 Brazier 不同”会重新拆层，不写死 11 根火舌/PPU/朝向。
- “只更新 skill”不修改作品资产，不运行 Build，不追溯捏造性能通过。
- “制作/导入新特效”复用唯一工作场景，Unity 专属资源收在该特效根目录并分类，
  不创建 Scenes 或 Editor，不恢复旧 Build 菜单；调参通过原生 Inspector，使用文档只写用法。

文档校验与流程走查只能验证技能结构/决策边界，不是新的效果或性能验证证据。
